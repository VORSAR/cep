# ADR-0015: Build-time architecture enforcement — the hostile gate

## Status
Accepted (owner condition at the 2026-11-01 baseline ratification). **Revised 2026-11-01** after two adversarial reviews of this ADR itself — the gate red-team ([review/gate-redteam.md](../review/gate-redteam.md), 25 findings) and the foundation consistency review ([review/foundation-consistency.md](../review/foundation-consistency.md)) — with four owner decisions logged in [decisions](../../sprints/decisions.md#owner-decisions-2026-11-01--foundation-adversarial-review-gate-red-team--consistency-review): the LAW Δ law-manifest mechanism adopted; goleak + apidiff approved as dependencies (≠ recommendation); the hostility bar reworded honestly; the review-only residue (§3.6) accepted knowingly.
Mechanisms are synthesized from two of the owner's prior projects, studied 2026-11-01 and verified first-hand; they are referred to here only as **reference A** (architecture-rules-as-tests, non-vacuity doctrine) and **reference B** (registry-driven gate, planted-failure proofs, suppression accountability) and are never named in this repository.

**This ADR is the gate's single normative mechanism catalog.** DEVELOPMENT.md holds the doctrine (the four gate rules, the suppression and TODO policies) and points here; ADR-0005 §2 points here; where any other document sketches a registry schema, a tier assignment or an instrument scope that differs from this file, **this file wins** (consistency review S1/S2).

## Context
DEVELOPMENT.md pins the gate's skeleton (registry, tiers T0–T4, collect-all, zero-is-failure, watchdogs, suppression metadata, toolchain parity). ARCHITECTURE.md §2b names eight review-blocking quality rules, the first four mechanically gated. This ADR is the missing half: **which mechanisms make those words executable**, such that (a) every architectural constraint has an instrument or is named in the review-only residue (§3.6), (b) every instrument is proven able to fail, and (c) the sum meets the owner's bar, honestly stated (§3.7): *every freestyle shortcut is either mechanically red or a named loud row at merge.* Reference A's doctrine governs: *"an invariant without an instrument is a claim, not a property"*; reference B's governs the gate: *"a check that can't fail isn't a check."*

The red-team's root finding (GR-01) shapes this revision: **every rule the gate enforces lives in repo files the policed code's authors can edit**, and the merge review is the only remaining net. The gate therefore cannot be self-protecting; its design goal is that no law change is ever *silent* (§1.3), and the floor of the whole design is stated plainly: **the owner reads the LAW Δ block at every merge** (GR-12 accepted honestly).

## Decision

### 1. One registry, one runner, one law manifest

**1.1 Registry and runner (reference B).** `gate/registry.json` rows are executed by `gate/run.sh` identically from hooks, `make check|combine-check|strict-gate`, and CI. The row schema — **the single normative statement; DEVELOPMENT.md and ADR-0005 cite it**:

```
id            unique instrument/step id (string)
job           the CI job that runs it
tiers         subset of {T0,T1,T2,T3,T4}
blocking      true | false (false = advisory; advisory rows age, §3.9)
timeout       per-step watchdog (TERM then KILL, process group)
needs         ids that must complete first (DAG, validated by registry-lint)
scope         file classes the step sees: subset of {prod, test, bench, tools, proofs, generated} (§2.1)
expected_scope a `git ls-files` glob or `go list` pattern; the runner expands it LIVE and
              fails when the step's covered-count ≠ the expansion (GR-13 — "n ≥ 1" is not a floor)
min_wants     analyzers only: the minimum number of `// want` expectations in the
              analyzer's fixture; the teeth meta-test asserts it (§3.8, GR-04)
lands_in      the sprint that builds this row (§2.2, GR-20)
exclusive     true | false (default false) — true = the row runs ALONE: no other row
              runs while it does (benchmarks, latency measurements, stress-under-load
              rows; anything whose result depends on machine load) — added 2026-11-02
command       what runs
```

*(Annotated 2026-11-04, owner decision at S2.2a: `tiers` may also hold `nightly`. A nightly row runs only in a second generated workflow, `.github/workflows/nightly.yml`, on a schedule and by hand, never on a pull request; `summarize` judges it as it judges T4. First use: `fuzz-parser`, advisory, aging as a known-issues note until the gate has persistent advisory state.)*

**Parallel by default (owner requirement 2026-11-02: "build and tests run in parallel where they can to reduce time").** The runner executes rows **concurrently**, bounded by a worker limit (default: the CPU count; overridable), starting a row as soon as every row in its `needs` has completed; an `exclusive` row waits for all running rows to finish and runs alone. Collect-all, watchdogs and zero-is-failure are unchanged; the summary lists rows in **registry order, never completion order** (deterministic output), and its footer prints the run's wall time beside the sum of step times, so the parallel saving is visible. Inside rows, Go does its own parallelism: `go build`, `go vet` and `go test` run packages concurrently (`-p` = CPU count), tests call `t.Parallel()` unless they state why not (testing.md rule 3), and every row shares one Go build and module cache. In CI, the `job` field maps rows to **separate GitHub Actions jobs that run concurrently** (e.g. lint, unit+coverage, race, grammar differential, the two-OS determinism leg), each restoring the module and build cache keyed by `go.sum` + the `tools.json` hash; the summary job still `needs: all`. Parallelism must never change a verdict: a check that passes alone and fails in parallel is a flaky check — broken, fixed at the root (ground rule 11).

*Annotated 2026-11-02 (owner decisions at S1.1a's plan check, [decisions](../../sprints/decisions.md#owner-decisions-2026-11-02--s11a-plan-check-g0); ≠ the Go-runner recommendation): the runner is **stdlib Python run by a pinned CPython (3.15.2)**, not POSIX shell. So are the summary, the installer, parity, coverage, the hooks and the CI-workflow generator.*
- *Every entry point goes through `gate/bootstrap.py`. It is one file that any `python3` ≥ 3.9 can run, and it installs the pinned tools and then `exec`s the pinned interpreter with `-I -B` on `gate/run.py`.*
- *Every gate verdict comes from the pinned interpreter.*
- *Records are keyed by job and row (`records/<job>/<id>.json`). Parity is a built-in first step in every job, and the one hard stop.*
- *The CI workflow is generated from `registry.json` and checked by regenerate-and-diff, so registry-lint (§1.2) never needs a YAML parser.*

*"`gate/run.sh`" in this ADR now means that entry point. The design: [s1-1a-plan-check.md](../../sprints/s1-1a-plan-check.md) §2.*

*Annotated at S1.1a-1's G1 (2026-11-02; the design is [s1-1a-gate-design.md](../../sprints/s1-1a-gate-design.md) §3–§5):*
- *`expected_scope` has three kinds:*
  - *`git`: complete pathspecs, magic included;*
  - *`go`: real packages only;*
  - *`go-vet-units`: what `go vet -json` really counts.*
- *`{files}` passes the path of a NUL-separated list file.*
- *For a row that is not an analyzer, `min_wants` is the minimum covered count. It is how `proofs` pins its driver count.*
- *Parity writes one record per job.*
- *Parity re-hashes every pinned executable on every run. At T2 and above it also checks each tool's whole-tree digest, `tree_sha256` in `tools.json` (owner, at G1).*

*Annotated 2026-11-03, S1.1a-1 as built ([record](../../sprints/s1-1a-1-record.md#findings)):*
- *The entry is two files. `gate/bootstrap.py` parses under Python 3.9 only to refuse an older interpreter with the fix; the installer it runs needs ≥ 3.12. The pinned interpreter runs with `-I -B -X utf8`.*
- *The registry is `{"schema": 1, "rows": [...]}`, and the watchdog field is `timeout_s`. The id `parity` is reserved for the built-in step.*
- *Each row runs in `<run_dir>/rows/<job>/<id>/` with `GATE_TIER`, `GATE_ROW`, `GATE_RUN_DIR` and `GATE_ROW_DIR` set.*
- *Every record carries `blocking`, so a WARN (a non-blocking `"fail"`) reads as one without the registry (owner, review BA12). `run.json` carries `registry_sha256`.*
- *A red row's reason carries its own first failure line, and the summary names the run directory (owner, review BA3).*
- *The runner drops every `PYTHON*`, `RUFF_*` and `GIT_*_PATHSPECS` variable: a pinned tool's own settings never reach a row (review BA2). S1.1b's golangci-lint row follows the same rule.*

*Terminology (consistency review S1):* the anti-vacuity check above is the row's **expected scope**; the word "coverage" is reserved for the statement-coverage instrument (`coverage-inclusion`). The two are different mechanisms and are never conflated again.

**1.2 Registry-lint** (itself a row): every row's CI job exists in the workflow YAML; every `needs` names a real row and the graph is acyclic; timeouts are well-formed; each CI job's timeout ≥ the sum of its rows' caps **+ 20%, minimum 60 s margin** (pinned — GR-23); every id in this ADR's §2 table exists in the registry, `blocking: true`, at its stated tiers, once its `lands_in` sprint has merged (GR-11 — deleting or demoting a row trips registry-lint, not just review). The CI summary job (`needs: all`, `if: always()`, the ONLY required check) turns a missing/stale/duplicate/malformed per-step record, or a skipped job, into a **named RED row** — a skipped gate is never a passed gate. The summary logic ships with fixture trees (planted problems) it must classify correctly. **Branch protection (the required-check name, no force-push to `main`) is owner-side GitHub state the repository cannot grant itself; it is recorded in the sprint record, and its absence is a standing known-issue, never assumed** (GR-12). *(Annotated owner, 2026-11-05 ([decisions](../../sprints/decisions.md#owner-decisions-2026-11-05--branch-protection)): no status check is required on `main`; the `protect-main` ruleset (deletion and force-push blocked) stays. The summary job is the one check to read.)* *(Annotated 2026-11-12, S1.1c-2 as built ([design](../../sprints/s1-1c-2-design.md) §4.2): registry-lint is `registry.py`'s validation, the generator's job timeouts with `ci-fresh`, and the **instrument pin** — `gate/law.json`'s `instruments` holds one row instrument per registry row (its tiers, `lands_in`, `min_wants`, `expected_scope`, code and proofs with their planted-case counts) and five Go-test instruments; `gate/runner/tests/test_instruments_pin.py` checks them against the registry and the real proof files at T2. The §2 ids below are not pinned as written; the as-built ids are.)*

**1.3 The law manifest and the LAW Δ block (GR-01 — the systemic countermeasure; owner-adopted 2026-11-01).**
`gate/law.json` enumerates every **law path** — the files whose content *is* the rules: `gate/` (registry.json, run.sh, the summary logic, regen-baseline, law.json itself), `.github/workflows/`, `tools.json`, `tools/deps-allowlist.json`, `tools/allowlists/*.json` (§3.10), `tools/importcheck/rules.json`, `tools/analyzers/**` (sources **and** `testdata/` fixtures), `api/exports.golden`, `api/clock.golden` (*added 2026-11-02: `internal/clock`'s exported signatures, captured at the clock freeze — S3.3's G5*), `gate/current-sprint` (*added 2026-11-02: the machine-readable current-sprint marker `todocheck` reads*), `docs/language/grammar.lark`, `docs/language/grammar.ebnf`, `docs/language/SPEC.md`, `docs/language/SEMANTICS.md`, `docs/language/errors.md`, `docs/architecture/ARCHITECTURE.md`, `docs/architecture/adr/`.
An always-on row (`lawdelta`, every tier, never skipped) diffs the law paths against the **merge base with `main`** and prints a **`LAW Δ` block at the top of the summary table**: per changed file — path, +/− line counts, and for structured files a one-line semantic delta ("rules.json: +1 edge `expr → runtime`"; "clockcheck allowlist: +`internal/pattern`"; "exports.golden: +3 exports"; "SPEC.md touched — **the spec is frozen; a change requires an owner decision**", GR-14). The row is **YELLOW, never blocking** (law must remain changeable) and **never absent** — an empty delta prints `LAW Δ: none`. *(Annotated 2026-11-11, S1.1c-1 ([design](../../sprints/s1-1c-1-design.md) §2): built as `gate/law.json` — every tracked law path with its kind and, for a document, its flag — and the `lawdelta` row (T1–T4, the `lint` job, the merge base with `main`). As built the row is **`blocking: true`** (owner, 2026-11-10, S1.1c's scope, 9): a delta of any size passes; it is red only when it cannot read — no merge base (never the silent pass), a listed path git does not track, a parser crash. The block is the summary renderer's own required argument, carried from the row's record (`law` on every record, schema 2; CI's aggregator requires the schema number), printed first at every tier. Its texts: the block itself (one line per changed law file — a semantic one-liner per structured kind, a document's first changed heading with its flag and a hunk count, `code` and `workflow` grouped last, one line per entry), `LAW Δ: none`, `LAW Δ: HEAD is main — read the PR run`, `LAW Δ: FAILED — see the lawdelta row`, `LAW Δ: not run — the lawdelta row is not in this registry at <tier[, job]>`, and at a local tier `LAW Δ: <n> law files have uncommitted edits (not shown)`. `gate/sprints.json` (the plan's rows in order) and `conformance/notbuilt.json` joined the law paths; `tools/allowlists/*.json` does not exist and is not listed (S1.1c-2); the as-built analyzer is `tools/archcheck/`, listed as `code`, as are `gate/ci/`, `gate/proofs/drivers/`, `ruff.toml`, `go.mod` and `gate/proofs/go.mod` (owner, 2026-11-11, the fix round).)* The owner's check (sprint model §8 step 10) carries the standing line: **"LAW Δ block read and intended."** This converts the gate's worst defeat class — a self-consistent edit of code + rule in one commit, green everywhere — into a handful of loud lines in the one place the owner already reads (16 of the red-team's 25 findings reduce to this hole; GR-02/03/04/05/11/12/14 are closed or contained by it).

**1.4 Law-file ownership (GR-18).** The coordinator owns `gate/`, `tools/*.json`, `tools/allowlists/` and `tools/importcheck/rules.json` in every sprint's lane roster. Agents never edit law files in their lanes; a lane that needs a law delta (a new allowlist entry, a registry change) states it in its lane report and the coordinator applies it on the integration branch, where the `LAW Δ` block then shows the sprint's law changes as one reviewed set. *(Annotated 2026-11-02, owner decision at S1.1a's plan check, ≠ R: in **S1.1a-1 and S1.1a-2**, which build the gate itself before LAW Δ exists, build agents write the gate's code. The coordinator reviews it, with a human gate (the owner decides) wherever the coordinator is uncertain. The coordinator still owns the law data: `gate/registry.json`, `tools.json`, `go.mod`, `ruff.toml`. S1.1b asks the owner again for its analyzer lanes.)*

### 2. Architecture constraints as analyzers with teeth (reference A, in Go)

*(Annotated owner, 2026-11-04, S1.1b slimmed ([decisions](../../sprints/decisions.md#owner-decisions-2026-11-04--s11b-slimmed-toward-engine-code)) and S1.2 cut ([decisions](../../sprints/decisions.md#owner-decisions-2026-11-04--s12-cut-to-the-model-kernel-and-spec-rev-3)): `importcheck`, `clockcheck`, `puritycheck` and `globalscheck` are four checks of one standard-library program, `tools/archcheck` (`go/parser`; no `go/analysis`, no `x/tools`), run by one row, `archcheck`, at T0–T4, reading `tools/importcheck/rules.json`; its named purity exceptions live in its code. `law.json`/`lawdelta` and the LAW Δ block, registry-lint, `todocheck`, `testhygiene`, the teeth meta-test, golangci-lint `smells` + `nolintlint`, the suppressions checker with the allowlist grammar, the dependency-allowlist, licence and `govulncheck` checks, the build-tag law, the weekly canary, `gate/current-sprint` and `docsync` (a) and (d) move to S1.1c, which runs after S3.3. `gate/registry.json` lists the rows that exist.)*

**2.1 Scope classes and the generated-code policy (GR-07/GR-09/GR-19, consistency B6/S9 — decided now, not discovered as friction).**
Every first-party file belongs to exactly one class; each registry row's `scope` says which classes the step sees, and registry-lint asserts the row's command matches:

- **prod** — library and binary code.
- **test** — `*_test.go` and `testdata/`. `funlen`, `gocyclo`, the file ≤ 500 and params limits **do not apply** here (table-driven tests are the project's idiom; GR-09); `errcheck`, `gocritic`, `forbidigo`, import and clock rules still do.
- **bench** — `bench/`. Out of scope for `clockcheck` and `testhygiene` (ADR-0010 §8's open-loop generator MUST pace on the wall clock); in scope for `importcheck`.
- **tools** — `tools/`, `gate/` scripts. Gated by `smells` and `testhygiene` only. *(Annotated 2026-11-02, owner decisions at S1.1a's plan check: the gate's own code is Python, which those Go analyzers cannot see. It is gated instead by `ruff` (pinned 0.17.3; format + lint, incl. a ban on `time.sleep` outside the one wait helper), by `pyfloor` (the bootstrap parses at Python 3.9), and by `pytests` (the gate's own tests, zero-is-failure). It has no statement-coverage floor: residue item 8 in §3.6.)* *(Annotated 2026-11-03, S1.1a-1 as built: `pyfloor` runs the floor modules' own tests under the pinned CPython 3.12.16, and ruff's per-file `py39` target holds `bootstrap.py` to 3.9 syntax.)*
- **proofs** — `gate/proofs/` (§3.4). Deliberately defective code; out of scope for every analyzer; runs only under the T4 proof rows.
- **docs** *(added 2026-11-06, [owner](../../sprints/decisions.md#owner-decisions-2026-11-06--the-docs-restructure))* — the tracked Markdown under `docs/`, plus `CLAUDE.md` and `README.md`. Seen by the `doclinks` row (T1–T4) only: every relative link and `#anchor` resolves against what git tracks, so a local run and CI agree.
- **generated** — any file whose first line matches the canonical header `^// Code generated .* DO NOT EDIT\.$`. **Exempt** from `smells`, `globalscheck`, and excluded from the coverage numerator **and** denominator; **in scope** for `importcheck`, `clockcheck`, `puritycheck` (a generated file importing `os` is still a bug). Anti-forgery (GR-07): `freshness` fails if any file bearing the header is not in its regeneration manifest — a forged header on hand-written code is caught because nothing regenerates it. Generators (`goyacc` wrapper, `kwgen`) MUST emit the header. *(Annotated 2026-11-12, S1.1c-2's fix round ([owner, review and break-it 3](../../sprints/decisions.md#owner-decisions-2026-11-12--s11c-2s-review-and-break-it)): the header counts only before the package clause (Go's own rule, `go/ast.IsGenerated`), and only on a file listed by path in `tools/allowlists/generated.json` (the one grammar; empty today). archcheck gives a marked file that is not listed every check and the finding `generated: the file says it is generated but tools/allowlists/generated.json does not list it`; a listed file without the header is a stale target; the coverage floor leaves a file out only when both hold; the `suppressions` row counts each header as an in-code exemption. `freshness` is not built, so the list is the anti-forgery until it is.)*

### 4. What we deliberately do NOT adopt (differences argued, not drifted into)

- **No mutation-testing tool** (neither reference uses one). Stated honestly (GR-06 — the previous "same assurance" claim was false): the planted proofs prove **the gate's instruments** can fail, not that **product tests** can fail. Product-test assertion strength is guaranteed by a different mechanism: testing.md's first-seen-failing rule, the QA agent's independently written failing test at each plan check (sprint model §6/§8), and red-run evidence quoted in the PR. The whole-engine break-it before each release MAY add a sampled spot-check (flip one constant per package; the suite must go red) — mutation testing scoped to where it matters, by hand.
- **No commit-message linting** (neither reference): the sprint model's one-PR-per-sprint and human merge govern history shape.
- **No coverage theater**: the 90% floor *(85% until the owner raised it on 2026-11-02)* is a tripwire under the binary inclusion rule, not the goal; inclusion is binary (allowlist-waivable with a recorded reason), the floor is unwaivable within its stated scope (§2.2), and assertion-free tests are called out as the residue they are (§4 first bullet — coverage proves execution, never correctness).
- **Dependencies (owner-approved 2026-11-01, ≠ recommendation; ADR-0009 amended):** `go.uber.org/goleak` (test-only, the leak proofs) and `golang.org/x/exp/apidiff` (build-time only, T4 API diff); `golang.org/x/tools` scope widened to include `go/analysis` + `analysistest` for the gate's analyzers. All pinned in `tools/deps-allowlist.json`.

## Consequences
- Positive: every architectural sentence either names its instrument or stands in the §3.6 residue the owner accepted — no third state; law changes are structurally loud (LAW Δ); drift between docs, registry, CI and code is itself a red build; agents receive failures that teach the fix.
- Negative: the gate is a real subsystem with its own proofs, **spread over S1–S3 by the `lands_in` column** (GR-20 — the previous "most of sprint S1" budget was impossible against ADR-0005's Stage 1; every instrument now has a named sprint and lands with its first subject); analyzer false positives cost accountable suppressions or allowlist entries (both loud), never rule deletions.
- Accepted residual: with one human merger, the floor of the design is the owner reading the LAW Δ block (§1.3). The gate is hostile, not self-protecting — stated plainly by decision.
