# Grammar assurance — tooling & literature survey

Research note for L4/engine Phase 1 (owner request 2026-10-31: "make sure the grammar is iron-clad tight, no uncertainties; Go frameworks preferable"). Sources accessed 2026-10-31.

## The governing fact from the literature

General CFG ambiguity detection is **undecidable** (Basten, *Ambiguity Detection for Programming Language Grammars*, CWI; AmbiDexter papers, Basten & Vinju / van der Storm, LDTA 2010). Consequence: you cannot *test* your way to an unambiguous grammar — you **construct** one, by keeping the grammar inside a deterministic class and letting the generator's conflict analysis be the proof:

> **A grammar that builds LALR(1)/LR(1) with zero conflicts is deterministic, and every deterministic CFG is unambiguous.** That machine-checked build is the "iron-clad" guarantee; everything else is additional assurance.

Our syntax rules already keep us in that class by construction (R13: <60 productions, LALR(1), reserved keywords, no context-sensitive lexing).

## The layered plan

| Layer | Tool | What it proves |
|---|---|---|
| 1. Normative spec grammar | **Lark** (Python) via the skill's `grammar_check.py` — already in hand | LALR build **fails on any conflict** (the unambiguity proof); corpus re-parsed with Earley `ambiguity='explicit'` (any sentence with two parse trees is reported); invalid-corpus must fail with expected error codes; rule-count cap tracked |
| 2. Engine parser (Go) | **goyacc** (`golang.org/x/tools/cmd/goyacc`) — recommended | Same LALR conflict check on the implementation side; the `.y` grammar is derived from the normative EBNF |
| 3. Differential testing | spec parser (Lark) vs engine parser (goyacc) over the full corpus + generated sentences | any accept/reject or tree disagreement = spec bug; "tests are the spec" applied to the grammar itself |
| 4. Corpus generation | Purdom-style production-coverage sentence generation + grammar-based fuzzing (Go native fuzzing with grammar-derived seeds); mutation for negatives | every production exercised; parser crash-freedom |
| 5. Round-trip law | canonical formatter | `parse → format → parse` yields the identical tree for every corpus file (catches token-boundary/precedence surprises; formatter doubles as the canonical-form enforcer, R15) |

## Go framework survey (owner preference: Go)

- **goyacc** — LALR(1) Yacc port maintained in `golang.org/x/tools`; **the** precedent for SQL-like languages in Go: CockroachDB's SQL grammar, Vitess's SQL parser, and Prometheus PromQL all use it. Reports conflicts (our proof mechanism). BSD-licensed, zero runtime deps. **Recommended.** Known cost: Yacc ergonomics are dated; error messages need our own error-catalog layer anyway (R14), so this costs little.
- **gocc / gogll** — LR(1)/GLL generators ([gogll self-comparison](https://github.com/goccmack/gogll)); technically fine, much smaller communities than goyacc. Fallback options.
- **ANTLR4 Go target** ([official Go runtime](https://blog.gopheracademy.com/advent-2017/parsing-with-antlr4-and-go/)) — ALL(*) is powerful but **resolves ambiguities silently by alternative order** and needs Java at build time. Silent resolution is the opposite of iron-clad; rejected for the engine, fine never.
- **participle v2** ([alecthomas/participle](https://pkg.go.dev/github.com/alecthomas/participle/v2), actively maintained — Debian migrated 2.1.4 in June 2026) — elegant struct-tag recursive descent, but the grammar lives in Go code, there is **no conflict analysis**, and left recursion is unsupported. Good for prototypes/internal tools; not for a spec'd language. Rejected as the normative parser.
- **pigeon / PEG generators** — PEGs are "unambiguous by construction" only because **ordered choice hides ambiguity silently**: reordering alternatives changes the accepted language with no warning. That is concealed uncertainty, not absence of it. Rejected.
- **tree-sitter** — GLR, error-tolerant; wrong properties for the normative parser (GLR tolerates ambiguity) but the right tool for *editor* tooling later. Non-normative, Phase 5.
- **AmbiDexter / Dr. Ambiguity** (CWI) — approximate ambiguity search for grammars *outside* the deterministic class ([CWI publications](https://ir.cwi.nl/pub/18675/18675B.pdf), [overview](https://www.cwi.nl/en/news/cwi-develops-better-techniques-detect-ambiguities-in-programming-languages/)). We only need this if we ever leave LALR(1); staying inside the class is the stronger guarantee. Noted, not adopted.

## Decisions this implies

1. L4 gate unchanged and sufficient on the spec side: `grammar_check.py` green = LALR conflict-free + Earley-ambiguity-clean corpus + negative corpus.
2. Engine Phase 1: parser generated by **goyacc** from a `.y` grammar derived from the normative one; the generated parser's conflict-free build runs in CI. *(New dependency: `golang.org/x/tools` at build time only — owner sign-off at engine start per ground rule 3.)*
3. Conformance suite grows a **grammar-differential job**: spec parser and engine parser must agree on every corpus file and on coverage-generated sentences.
4. The canonical formatter ships with the parser, and round-trip idempotence is a CI law.
