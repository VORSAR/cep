## Checked and holding

1. **The overflow conditions are exact.** Scratch `zz_review_test.go` builds each `arith` kind (int `+ - * / %`, timestamp ± duration, duration ± duration, duration × int, int × duration, duration / int), plus `neg` (int, duration) and `abs` (int), on literal operands. It compares every result with `math/big`, using `Quo` and `Rem` (truncated division, as Go). An out-of-range result must give a `*RuntimeError` whose message contains "integer overflow" and a null of the node's type. A result that fits must give the exact value, the right kind and no error. Division by zero must stay its own error. Results:
   - All pairs of 116 boundary values, including ±2^31, ±2^32, ±2^62, ±3037000499/500 (√2^63), MaxInt64/2 and /3, the event timestamp bounds and their ±2 neighbours: 161,820 evaluations; 130,870 exact, 30,602 overflow, 348 division by zero.
   - 400,000 random pairs, mixed uniform and random bit-length: 6,000,000 evaluations; 5,280,282 exact, 610,581 overflow, 109,137 division by zero.
   - Products near √2^63, and every power of two times every power of two (±1 and both signs): 54,579 evaluations.
   - All passed, exit 0.

   `mulInt` covers both MinInt64 × −1 orders: −1 × MinInt64 needs the explicit check because `r/x == y` holds after the wrap. `divInt` runs only after the zero check. `%` never overflows, and Go gives MinInt64 % −1 = 0. I ran this on arm64. On amd64 the Go spec defines the same result; I did not run it there.
2. **Every operation in the owner's list is checked:** `+ - * /` and unary `-` on ints, `abs`, duration ± duration, duration × int, int × duration, duration / int, unary `-` on a duration, timestamp ± duration. Nothing the code types is left unchecked: `arithNode` has no other integer kind, and `abs` of a duration is a type error.
3. **No result that fits changed.** That is the "exact" rows above, plus QA's in-range table rows.
4. **No allocation on the path that fits.** `testing.AllocsPerRun` gives 0 for all 12 arith kinds, both `neg` kinds and `abs`. The overflow path allocates 3, which shows the measurement can see allocations at all. The message is built only in `arith.overflow` and the two unary branches.
5. **The error reaches the rule as an error.** Every node that has children propagates a child's error before looking at null: `logic`, `not`, `isNull`, `compare`, `coalesce`, `extreme`, `cast`, `ifThenElse`, `member`. So `coalesce(i * j, 0)` and `(i * j) is null` cannot hide an overflow. Plan counts the error in `Stats.Errored` and drops the event for that rule (plan.go:344–347, 359–362). An int widened to a float output is converted only after the error check (plan.go:364). Short-circuit `and`/`or` and `ifThenElse` skip unevaluated operands, as they already did for division by zero; that is deterministic, and no rule acts on a value it never computed.
6. **The live test and replay agree.** `TestOverflowDropsTheEventForThatRuleOnly`, `TestOverflowIsAnExpressionError` and the keyword tests pass under `-race` (`go test -race -run 'Overflow|Keyword|Spec|Reserved|Alloc' ./internal/expr/ ./internal/parser/ ./internal/playback/`, exit 0).
7. **Other 64-bit arithmetic a rule can reach:**
   - **Duration literals:** checked at parse (`count > (MaxInt64-total)/unit`, E-DUR-002; lower.go:482).
   - **Int literals:** `ParseInt`, out of range is E-TYPE-001 (lower.go:447). A signed literal negates a value of at most MaxInt64, which cannot overflow (lower.go:413). MinInt64 cannot be written as a literal, so the language rejects it rather than computing a wrong value.
   - **Timestamp literals:** `time.Parse` RFC 3339, years 0000–9999.
   - **Event ints and durations:** exact `parseInt` (decode.go:364–396). Event floats: `ParseFloat` with its range error. Event timestamps: RFC 3339, so the bounded year range.
   - **Casts:** float→int is range-checked (nodes.go:618) and string→int uses `ParseInt`.
   - **Promotion:** int→float (`promote`, plan's `widen`, mixed comparisons) loses precision above 2^53 but never overflows. That is SPEC §5.10's stated promotion and outside the decision.
   - **Params:** substituted as typed literals and parsed by the same lowerer. `as()` makes int→float the same way.
   - **Not built yet:** text operators, `count` and `chain` are `later` nodes, and the aggregates are forwarded to S8.
8. **The engine's own arithmetic on event times saturates or is safe:**
   - `clock.add`/`clock.sub` saturate at both bounds (clock.go:29–49) and are used for the admission watermark, idle floors and the virtual floor.
   - `partition.addSat` (ts + TTL, guarded by `ttl > 0`) and `plan.addSat` (anchor + `every`, guarded by `every > 0`) saturate.
   - `add(m, 1)` (clock.go:183) saturates.
   - The rest is index and counter arithmetic.
   - No value a rule computes reaches a clock: a plain rule's output `ts` is the input's `e.Ts` (plan.go:369–370), and selecting `ts` is E-SEL-001.
   - Patterns (`within`, absences) are not built yet.
9. **The reference executor matches Go.** `checked_int64` truncates `/` toward zero, gives `%` the dividend's sign, keeps division by zero its own `ExpressionError`, and range-checks after computing exactly. A differential test runs Go's `arith`/`neg`/`abs` over 416 values × 416 values × 5 ops plus unary ops, writes the results to a file, and has Python's helper check each one (`zz_dump_test.go` + `zz_diff.py`): `compared 866112 mismatches 0`, exit 0. The harness passes: `all 50 checks passed`, exit 0. The new check is red-first by construction: it imports `executor.checked_int64` and fails if that is missing. The helper is a stand-alone pin, since the executor has no expression evaluator (reading 5), so it does not cross-check the engine. That matches the design note.
10. **Documentation that holds.**
    - SEMANTICS §2 (the time clause) matches SPEC §4.2 and E-TIME-001's fix.
    - §2.1 and §11.10 match SPEC §4.2 and errors.md on scope, apart from R4's wording.
    - §6.5 (`once`, E-PAT-003) matches grammar.lark `restart` and errors.md, apart from R1's section reference.
    - §10 matches SPEC §5.6.
    - E-SEL-001's new wording matches the readings and example 08.
    - E-IDLE-001's addition matches SEMANTICS §9's S3.2b-1 annotation.
    - SPEC §0 (rev 6), §5.6, the rev 6 change log ("the grammar is unchanged": true, the diff touches no grammar file) and DESIGN.md's log line agree with one another.
    - Appendix B's list equals grammar.lark's NAME exclusions as a set (115, sorted, none missing or extra; Python check above), and the test pins it through `keywordList`, which `TestKeywordsEqualGrammarLark` pins to grammar.lark. SPEC §2.1 already states that reserved words are reserved in any case.
    - I searched docs/language for "wrap", "overflow" and "two's complement": no text says integers wrap.
11. **Scope.** Every code change serves item 3. The doc changes serve items 1–2 and SPEC rev 6. The bookkeeping (the decisions entry, the history line, S3.2b-2's main-CI tick, the S8 and S5.1 forwards, the status line) is G0 and close-out housekeeping. Nothing beyond the card is built. The only thing missing for exit is G5 work: known issues S2.2b-1 and S3.2b-1-1 are still open in `docs/product/known-issues.md`, and the record's G5 box already covers closing them.
12. **Design.** One helper per operation, shared by ints, durations and timestamps, is the right call: the rule is written once, nothing changed outside `internal/expr`, and the existing per-rule error path does the dropping and counting. The extra division in `mulInt` costs a few nanoseconds per `*`, which is acceptable; a `math/bits` version would be faster but is not worth the complexity. The helpers are unexported. S8's forward says the aggregates "use internal/expr's checked arithmetic", so that works only if the aggregates live in `expr`; otherwise S8 has to export the helpers. That is for S8's design and needs no change now.

## Owner questions

1. **R2: the arithmetic list in SPEC §5.10.** The engine already accepts "a number times a duration" and "a duration divided by a number", but the spec's typing paragraph mentions only "a duration times a number". Separately, SEMANTICS promises "a time minus a time gives a duration", which the engine refuses.
   - **Recommendation:** in rev 6, add the two accepted forms (and unary minus) to §5.10, and delete the "time minus time" line from SEMANTICS. That describes what is built and changes no verdict.
   - Pro: the spec matches the engine now, while the spec is open for rev 6 anyway.
   - Con: it goes slightly beyond the five listed contradictions.
   - The alternative is to forward both to the backlog as a known issue. That keeps the sprint exactly to the card, but leaves a spec the card's goal says should agree with the code.
2. **R3: the "past year 9999" forward.** A time can also run off the other end, before year 0000 (e.g. an event time minus a very long duration), and the output encoder writes that as a negative year that is not a valid timestamp either.
   - **Recommendation:** annotate your S5.1 forward and the plan-check decision as "outside years 0000–9999". This adds no work now.
   - Pro: S5.1 handles both ends at once.
   - Con: none beyond one annotation.
