## Failure scenarios (blockers and should-fix)

- **Q1.** A later sprint breaks the scheduler so that `exclusive` is ignored. `make check` and CI stay green because no row runs the Python tests. Exit 3 was proven once by hand and is never re-proven. The same happens if a new test file lands in a directory without `__init__.py`: it never runs and nobody sees.
- **Q2.** CI downloads the three jobs' artifacts. Either the summary reports "duplicate parity" on every run, so exit 1 never passes. Or the files merge, `test`'s failed parity is overwritten by `lint`'s pass, and the unit verdict from the wrong Go is reported green.
- **Q3.** Someone moves `vet` to a new job `analysis` but forgets the workflow. The summary takes its job list from `--jobs lint,test,proofs`, sees no `vet` record expected, and passes. "CI shows the same rows" is false and nothing is red.
- **Q4.** Lane D adds `TNull` at iota 0 (or moves nullness into `Kind`). QA's null rows still pass, because they test struct literals they built themselves. The representation drifts from ARCH §4 with a green exit 7.
- **Q5.** The coverage tool compares with `>` instead of `>=`. The 9/10 case is written after the code, and its author copies the tool's output as the expected value. The test never failed first, so it can never catch the bug.
- **Q6.** The temp repo lacks `gate/registry.json`. The hook exits 1 for that reason, "commit refused" is asserted, and exit 5 is ticked while the gofmt check itself is broken.
- **Q7.** The runner builds a clean env for steps (to override GOROOT and friends) and drops `GIT_INDEX_FILE`. `git commit -a` with an unformatted edit is checked against the old index and accepted. This is the exact thing the owner's check tries.
- **Q8.** A developer stages one of five Go files. gofmt reports covered 1 against expected 5 and blocks every partial commit. Or someone widens the step to check all files and T0 starts reading the worktree.
- **Q9.** Lane A implements P2 as written. Parity fails, `vet` and `unit` still run with the system Go, and §6 13's "no other row starts" goes red. Lane A "fixes" it with an undocumented special case, or the owner sees verdicts from the wrong toolchain.
- **Q10.** The version comparison is a no-op. The proof's go1.27.2 manifest points at a cache directory that does not exist, parity fails "not installed", and the proof passes.
- **Q11.** With a 2 s cap, the two-worker rendezvous misses its cap under `-X dev` plus a CPU hog. That is a flaky red, which stops the line. With a 60 s cap, the 1-worker case costs 120 s per run, and the 50-run stress takes hours.
- **Q12.** The test pre-fills X's FIFO, so X ends within microseconds. A runner that starts Y eagerly sometimes shows Y after X anyway, and the test passes intermittently on a broken runner.
- **Q13.** The runner's thread-plus-subprocess tests are merged after one green run. Under CI load a watchdog race appears weeks later, which stops the line.
- **Q14.** The coordinator records max(job wall_ms) against the sum of steps. That number ignores queueing and job start skew, overstates the saving, and nothing checks it.
- **Q15.** `io` (a contracts-only package, 0 statements) lands, is absent from the profile, and fails "build failed". Or the tool reads the package-level `pass` as "tested", and a package with no `_test.go` passes the inclusion rule.
- **Q16.** The default scope pattern is mistyped (e.g. `internal/..` instead of `internal/...`). The proofs pass their own `-scope`, the real row evaluates nothing, and `internal/event` is never measured. Expected scope catches the zero only if the expansion uses the same broken pattern.
- **Q17.** A typo in the proofs row's discovery runs zero Python drivers. The planted package's Go test still ran, so "≥ 1 test" holds and the row is green.
- **Q18.** `vet` prints the count from its input list (`go list`) rather than from the packages it analysed. A build-tag-excluded package goes unvetted and the counts still match.
- **Q19.** Two worktrees install. The loser's `shutil.move` nests 70 MB inside the winner's tool directory. The race test passed because the two installs never actually overlapped.
- **Q20.** The hook's first stage uses a 3.10+ construct. CI (3.12) and the owner's shell (3.12.2) are green, but a commit from a GUI client (PATH = /usr/bin, Python 3.9.6) crashes the hook. The tarfile-filter difference changes extraction between the bootstrap and the pinned run.
- **Q21.** A Python runner test uses `time.sleep(0.2)` "to let the scheduler start". No analyzer ever flags it, and it flakes under load.
- **Q22.** A test opens a FIFO for writing and waits for a row that never started. `open()` blocks forever and the whole `pyunit` row times out without naming the test.
- **Q23.** The G2 box "every lane at T2" is ticked from `go test` runs of packages that contain no Python. The owner never agreed to that substitute.
- **Q24.** The test checks `killpg(pgid, 0)` right after the runner exits and finds a zombie not yet reaped by launchd. That is flaky. `KeyboardInterrupt` landing mid-record-write leaves a truncated JSON record.
- **Q25.** A fixture or a future row starts a background helper and exits 0. The runner waits for EOF on stdout forever, and the job times out at the CI level with no named row.
- **Q26.** The owner once ran `go env -w GOFLAGS=-mod=mod`. The gate's `go` honours it, and verdicts differ from CI's. A stray `json.py` on PYTHONPATH changes the gate's behaviour.
- **Q27.** The summary groups failing rows through a `set`. Output order changes with the hash seed, and the byte-identical test passes on most seeds.
- **Q28.** The coverage lane commits `testdata/exact90.out`. Git ignores it, the lane's tests pass locally, and CI fails with "file not found". Worse, a test that skips missing fixtures passes vacuously.
- **Q29.** 3.15.2 is pinned without verification or a recorded checksum source, and the installer's pin and the plan's pin can drift. Choosing a weeks-old minor is a trade-off the owner should make.

## Counter-examples to add to draft §6

Each has its expected outcome and the source it derives from. "Inferred" means a policy the sources imply but do not state.

**Runner**
- C1. The same fixture registry (no rendezvous rows) runs with `GATE_WORKERS=1` and with 4. Expected: the same verdicts and the same summary, apart from the time column and footer. Source: ADR15:39 "Parallelism must never change a verdict".
- C2. Y needs X. X is held. An independent row Z starts and ends while X is held (the witness). Then X is released. Expected: in the scheduler's trace, X.end comes before Y.start. A runner that starts Y eagerly is red on every run. Source: TM:30, SP:111.
- C3. An exclusive row E becomes ready while A and B run; C becomes ready later. Expected: E starts only after A and B end. C does not start while E waits or runs, so E cannot be starved (inferred). Source: ADR15:39 "an `exclusive` row waits for all running rows to finish and runs alone".
- C4. A step's leader exits 0 and leaves a background grandchild holding stdout. Expected: the runner does not hang, kills the group, and records fail "left running processes" (inferred). Source: DEV:28, TM:14.
