## Blockers

**A1 — law-file ownership decided without the owner.** ADR-0015 §1.4 is part of the owner-adopted LAW Δ design: agents never edit law files, and the coordinator applies law changes. The draft hands `gate/**` and the workflow to three agent lanes and justifies it with the go-engineer exception clause. That clause is in an agent definition, not in the ADR, so it cannot override a recorded decision (ground rule 4). *Failure scenario:* the owner reads §11, sees no question about this, and approves. In S1.1b the analyzer lanes do the same for `tools/analyzers/**`. The rule the red-team called "the systemic countermeasure" has then been waived twice, and the owner was never asked. The fix is one question. The practical answer is almost certainly yes, because the gate sprint cannot be built otherwise.

**A2 — the parity row breaks the summary.** Every CI job runs parity. Each run writes `records/parity.json`. The summary job downloads all records into one tree. Either the files overwrite each other (artifact merge) or the summary sees N records for one id and marks them "duplicate", as §6 case 41 requires. *Failure scenario:* Lanes A and C build exactly to the seams. The first CI run on the PR shows `strict-gate` RED "duplicate: parity", and exit 1 cannot pass. The coordinator then patches a special case at combine time, outside any test. The `"*"` value would also trip S1.1b's registry-lint as written in ADR-0015:43.

**A3 — the gate's own tests are not in the gate.** In the Go version, `unit` (`go test ./...`) also ran the runner's tests. Under Python it runs only `internal/event`. *Failure scenario:* the runner, installer, coverage and summary test suites pass on the lane branches. Nothing runs them at T2, T4 or in CI. A later edit to the summary classifier breaks fixture classification, and `strict-gate` stays green. Exits 1, 2, 3 and 6 are then "proven" once, by hand, and never again on `main`.

## Should-fix

**A4.** Every S1.1b instrument is a Go analyzer or golangci-lint. The gate's Python is invisible to all of them. *Scenario:* a runner test uses `time.sleep(0.5)` to "let the child start". It is flaky under CI load. Ground rule 11 stops the line, and no instrument would have caught it. ADR-0015 promises the owner either an instrument or an accepted residue for every rule.

**A5.** If P2's lean is implemented generically and every row `needs: parity`, then a toolchain mismatch still runs `vet`, `unit` and coverage with the wrong tools. The summary then shows real-looking verdicts beneath the parity failure. DEVELOPMENT:12 says such verdicts "mean nothing", so they must not be shown.

**A6.** On this machine, `python3` resolves to 3.12.2. A commit made from an IDE or GUI client gets a minimal PATH and resolves `/usr/bin/python3` 3.9.6 (inferred). CI uses 3.12 (inferred). *Scenario:* the bootstrap gains a `match` statement or `zip(strict=True)`. CI and terminal commits stay green. The owner's IDE commit fails with a SyntaxError inside the hook, and the hook cannot even name the fix.

**A7.** Python's `subprocess` turns "cannot reap the child" into exit status 0. *Scenario:* a helper or a later change ignores SIGCHLD, or reaps with `os.wait()`. A failing `go vet` row is then recorded as passed: a false green in the gate itself, which is the worst failure class here. Separately, a row that leaves a background grandchild holding stdout makes `communicate()` wait forever. The runner has no ceiling of its own, so `make check` hangs.

**A8.** *Scenario:* a malformed `registry.json` raises `KeyError` inside the runner. The process exits 1 with a traceback and no `exit:` line. The hook, CI and the agent read this as "gate failed". The verifier rule "read the `exit:` line" (ground rule 12) then has nothing to read.

**A9.** *Scenario:* the owner has `PYTHONPATH` set for another project that contains a `json.py` or `subprocess.py`. The gate imports it. Separately, every gate run writes `gate/__pycache__/` into the checked worktree, which ADR-0015:74 forbids. A stale `.pyc` can also mask an edit when file timestamps are coarse (inferred).

**A10.** *Scenario:* the summary classifier collects "missing" ids into a `set` and prints them. The output order changes between runs. Exit 3's identical-summary test fails one time in N: a flaky test that ground rule 11 stops the line for. Or the fixture-tree walk returns files in a different order on CI's filesystem, and macOS and CI disagree.

**A11.** *Scenario:* Lane C hand-writes idiomatic YAML. In S1.1b, registry-lint cannot read it with the standard library. The lane then either asks for a YAML dependency (an owner question, against ADR-0009's default) or writes a fragile line parser. Generating the workflow from the registry removes the drift that registry-lint exists to catch.

**A12.** *Scenario:* Lane A implements T0 by exporting only the staged `.go` files. That is fine for `gofmt`. In S1.1b, `importcheck` at T0 needs the staged package together with its imports, so it type-checks the worktree instead. A staged bad import is then hidden by a fixed but unstaged file, and S1.1b exit 2 passes by luck.

**A13.** *Scenario:* Lane B's coverage tool expects the profile at `.gate/coverage.out`. Lane A's `unit` wrapper writes it to a per-row temp directory. Both lanes pass their own tests. The combined T2 run fails "missing profile", and nobody owns the wrapper that should fix it.

**A14.** *Scenario:* Lane C starts W2 from the coordinator's first commit. It has no runner and no installer, so it stubs them to test the hooks. Its hook proof passes against the stubs and fails at combine. Branching W2 from a combined W1 also lets Lanes C and D be "done at T2", as the sprint model requires.

**A15.** Silence is not an answer under ground rules 1 and 2. G0 needs "answered by the owner: no open question". A default the owner never explicitly accepts leaves the record unable to show that a decision was made.

**A16.** ADR-0015:90 says "verified every run". A stamp proves only that an install once matched. *Scenario:* a cached tool directory is modified after install, by a stray build or an editor. Parity stays green because the stamp still matches the manifest.

**A17.** *Scenario:* a lane edits the `Makefile` so that `check:` runs `--tier T1`, or makes a hook exit 0 early. T2 then silently skips unit tests and coverage, and S1.1b's LAW Δ prints "none" because neither file is a law path.

**A18.** Agents briefed from a draft that still says `gate/run.sh` and Go structs will build the wrong thing. The ADR and ARCHITECTURE lines are normative, so they must be annotated (ground rule 4) in the same change as the answer. They must not be left to disagree with the code.

**A19.** *Scenario:* a go-engineer lane is told to write Python. It applies Go-only rules, skips the bootstrap floor and stdlib-only constraints it was never told about, and reports "done" by Go criteria.

**A20.** Pinning a version whose platform assets or licences were not checked repeats exactly what §0.6 guards against for Go. The 3.9 bootstrap also extracts the CPython archive with no extraction filter. Verifying the checksum first is what makes that extraction safe.

**A21.** If Python pushes the card over 13 and the split line is applied as written, S1.1b goes to about 14–15 points. That breaks the cap the owner just approved in v3.

**A22.** *Scenario:* QA writes `event.Compare(a, b)` with value arguments, and Lane D implements `Compare(a, b *Event)`. The tables are red for a signature mismatch, not for behaviour. Lane D may not edit QA's files, so the lane stalls.
