# Should the import law allow `internal/expr` → `internal/model`?

> **Historical — S2.2a, the grammar differential and the expression engine; merged in PR #6.** Not current: what is built is the code; the decisions it carried out start at [decisions.md](../sprints/decisions.md#owner-decisions-2026-11-04--s22a-runs-in-full); what is next is [sprint-plan.md](../sprints/sprint-plan.md#status). **This sprint:** [record](../sprints/s2-2a-record.md) · reviews: **the expr → model edge**. **← [S2.1](../sprints/s2-1-record.md) · [S2.2b](../sprints/s2-2b-record.md) →**

Adversarial architecture review, S2.2a. Read-only. Sources: ADR-0011, ADR-0003, ARCHITECTURE §2a/§3, `tools/importcheck/rules.json`, `internal/model/model.go`, `internal/event/event.go`, the S2.2a card. `internal/expr`, `internal/plan` and `internal/validate` do not exist yet; nothing in Go is affected today.

## Bottom line (3 lines)

1. ADR-0011 contradicts itself: decision 1 lists expr's imports without `model`; decision 2's `expr.Build(model.Expr, scope)` cannot compile without it. The design needs expr to read `model.Expr`; the import list was written for the operator exception and never checked against the signature.
2. The edge is downward (L2 → L0), makes no cycle, and no upward edge. It breaks only §3 rule 5's sentence "operators import event and clock only" and the exhaustive list. It is an exception by the letter of §3, not by the layer model of §2a.
3. Every alternative that avoids the edge needs a model → expr walk with two consumers (plan and validate) that have no shared home below them; each costs 150–300 lines plus a new seam that ADR-0003 already rejected once ("two models with a converter"). Recommend allowing the edge, narrowed to the expression types, with one rule in Build that keeps rule knowledge out of L2.

## 1. Does ADR-0011 require the edge? Real, or an accident of wording?

What the ADR says, verbatim:
- Decision 1: `internal/expr` "(imports: `event`, `text`, `table` — the only operator-layer package allowed these two imports; ARCHITECTURE §3 rule 5 gains this named exception)".
- Decision 2: "`expr.Build(model.Expr, scope) (Expr, error)` dispatches on node kind".
- Decision 4: E-NULL lints "run in `internal/validate` by walking the model expression ... validate and expr share the typing tables (exported from expr)".
- S2.2a card item 4: "typing for every SPEC §5.10 form ... exported to `validate`".

Decision 2 is a Go signature. A function whose parameter type is `model.Expr` needs `import "github.com/vorsar/cep/internal/model"`. So, as written, the ADR requires the edge. Decision 1's list omits it. Both were written on 2026-11-01; §3 rule 5, the exception table and `rules.json` all copied decision 1's list. Three documents say "no model"; one line of design says "takes model.Expr". That is an accident of wording, not two considered positions.

Which half is the accident? Test it: can expr do its job without seeing `model.Expr`?
- The job (decision 2): walk 13 node kinds (`model.ExprKind`), pick a specialized node per `(op, leftType, rightType)`, compile attribute names to `(slot, attrIndex)`, report E-TYPE-001 and E-FN-001 at build. The specialized-node table is bound to expr's unexported node constructors. Moving the walk out of expr means exporting every node constructor so another package can build the tree (§2b item 6 forbids exactly this: "a type exported solely so another package can poke its fields").
- The second consumer (decision 4, card item 4): `validate` must type every §5.10 form and emit the same E-TYPE/E-FN codes. If expr exports only tables keyed on `event.Type`, validate writes its own walk over `model.Expr`, and plan's Build writes another. Two typing walks over the same 13 kinds is the F6 hazard ADR-0011 exists to remove ("one owner for typing").

So the requirement is real: one walk over `model.Expr`, owned by one package, called by two L3 packages. The only package below both plan and validate that can own it is expr. That package must see `model.Expr`. Decision 1's import list is the accident.

Steelman for the other reading: expr was meant to be an *operator* like pattern and window, which never read the IR — the planner reads `model.Pattern`/`model.Window` and constructs them. On that reading, expr's builder belongs in L3 and decision 2's signature is the accident. This fails on the facts above: pattern and window have a handful of constructor parameters; expr has a 13-kind recursive tree whose compilation *is* the package. Expr is not an operator; it is the IR's expression compiler plus its executors, placed in L2 because its executors are pure domain logic. The operator rule was written with the other five packages in mind.

## 2. What goes wrong if the edge is allowed?

**Cycle or upward edge.** None. `model` imports only `event`. With the edge: `expr → model → event`, `validate → expr, model`, `plan → expr, model`. The DAG stays a DAG. Nothing points up.

**Is it even an exception?** By §2a ("a package MUST import only packages in layers below its own") L2 → L0 is permitted outright. By §3 rule 5 ("operators import `event` and `clock` only") and the exhaustive-list decision of 2026-11-02 it is red. The edge violates the *list*, not the *layer model*. The layer charter row for L2 says MUST NOT know "runtime; I/O; parsing; wall clock" — the IR is none of those. The charter row for L3 says "model + operators + clock; wires them" — this is the one real tension: §2a places *knowledge of the rule model* in L3. The edge moves a slice of that knowledge (expressions only) into L2.

**Does the operator layer see rule structure it should not?** Go imports are package-wide. Once expr imports model, it can name `model.App`, `model.Rule`, `model.Stream`, `model.Param`. The law cannot say "only `model.Expr`" — `archcheck` checks import paths, not selectors. The concrete hazards an agent could fall into during S2.2a:
- Resolving `${param}` inside Build by reaching for `model.Param` defaults (the IR keeps params unresolved, ADR-0003 §5; `Literal{Kind: LitParam}` and `TextOperand.Param` carry them). That puts deploy-time environment knowledge in L2.
- Resolving attribute names by reading `model.Stream.Attrs` instead of the `scope` argument (which should be `event.Schema`, so names become `(slot, attrIndex)` as decision 2 requires).
- Reading the `in` operator's `model.Expr.Table` string and looking the table up by name inside expr, rather than receiving a table handle from the planner.
All three are review-only today (the same class as the existing "interface-only" rows for `pattern → expr`, which the gate also cannot see). A cheap mechanical fence exists (option d below).

**Does it weaken the layering argument?** Slightly, and honestly. The sentence "operator packages import `event` and `clock` only" gains its third expr-only exception; expr's own ADR already calls it "a wide L2 package". ADR-0003 §3's "the validator and planner consume only `model.App`" becomes "validator, planner and expr". When `model.Expr` changes (a new node kind in Phase 2, e.g. FA11 extension calls), expr's switch changes with it — but that is true of whichever package owns the switch; the edge decides where the change lands, not whether it happens. Canonical-JSON stability of the IR is untouched: expr reads the struct, never encodes it.

**Testing consequence.** expr's tests must build `model.Expr` literals by hand (expr cannot import parser). Under every alternative they build the alternative's input tree by hand instead. Same cost.

Attack on (a), the recommendation: "it is the convenient choice dressed as the principled one." Answer: the inconvenience of the others is not cost alone; it is a *missing home* for the walk. Every option that keeps `model` out of expr either duplicates the walk in two L3 siblings or invents a package to hold it. The law would be defending a sentence (rule 5) at the price of the principle the sentence serves (one owner, no copy-paste, no tactical seams).

Attack on (b)/(c): "ADR-0003 already decided against a converter between two trees." Also: the S2.2a card is 10.5 of 13 points with no split line; 200–300 extra lines of seam plus tests pushes it to a split before G0 (ground rule 6), for a package boundary the layer model itself does not require.

Attack on (d1): most honest to the charter ("model knowledge lives in L3"), and the most expensive; the package would exist only to launder one import. §2b item 8 calls that a premature framework.

## 4. Recommendation for the owner (plain language)

Let `internal/expr` import `internal/model`, and write it into the law as a named row: "`expr → model` — expr is the IR's expression compiler; `Build` reads `model.Expr` only." Pair it with two fences. First, a rule in Build's contract: it MUST reject a `${param}` literal or text operand (resolution is the deployer's job, before Build), MUST take names only from its `scope` argument, and MUST receive table handles from the planner, never look tables up by name — so expr learns the shape of an expression and nothing about the rule, stream or deployment around it. Second, if a mechanical guard is wanted, the ~50-line selector fence in `archcheck` (option d2) makes "only the expression types" enforceable. The consequences, stated plainly: the sentence "operators import event and clock only" gets one more expr exception (it already has two); expr can technically name all of `model` unless the fence is built; and when the IR's expression node changes, expr changes with it — which is true wherever the compiler lives. In return the design keeps one typing walk with one owner, decision 2 compiles as written, S2.2a stays inside its 10.5 points, and the law does not grow a second expression tree or a package that exists only to hold a converter. The choice between (a) and (d2) is whether the "expression types only" fence is worth ~50 lines now; the walk's home is the same either way.
