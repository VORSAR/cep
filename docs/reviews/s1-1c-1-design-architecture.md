## Findings (ground rule 15)

### B1 — blocker: the `deps` row is red or green by the state of CI's module cache, not by the tree (§5.3)
Evidence: the row sets `GOPROXY=off` (§5.3; plan check S4). CI's setup (gate/ci/generate.py:57–69) restores `~/go/pkg/mod` under key `go-<os>-hashFiles(go.mod, go.sum)-<sha>` with a prefix restore key, and runs `make setup tools`; the Makefile has no `go mod download` (grep: none). The `lint` job's rows have no `needs` (gate/registry.json: lawdelta, vet, archcheck, …, deps all `[]`), so `deps` races `vet`/`archcheck`, the only rows that download modules. Probe on an empty GOMODCACHE: `go list -m -json all` → `go: module lookup disabled by GOPROXY=off` (three times). And `golang.org/x/exp` (the tool directive, counted as imported per §5.3) is only ever downloaded by the `apidiff` row, which runs at T4 only: at T3 on a PR whose go.sum changed (the first run after any dependency bump — exactly when the row matters) the cache is cold, `x/exp` has no `Dir`, and the row prints `deps: golang.org/x/exp: no source on disk; run: go mod download …` — a red that a re-run can turn green. Ground rule 11 calls that flaky.
Disposition: change §5.3 and §2.5/§6: generate.py gains `NEEDS_MODULES = frozenset({"deps"})` beside `NEEDS_HISTORY`; a job holding such a row gets a setup step `go mod download all` run in `.` and in `gate/proofs` (network at setup, as the checkout and tools already are; the row itself stays `GOPROXY=off`); `test_generate.py` gains `test_every_module_row_s_job_downloads_modules`. Locally the row's existing "run: go mod download <path>" text is the right answer. Alternative if the owner prefers no new setup step: `deps` declares `needs: ["apidiff"]` and moves to T4 — weaker (no T2/T3 check) and still a race with the proofs module's cache. Recommend the setup step.

### S1 — should-fix: a `lawdelta` PASS with an empty or absent `law.txt` contradicts itself (§2.5)
Evidence: `_read_law` returns `[]` for absent/empty; `_law_block` then prints `LAW Δ: FAILED — see the lawdelta row` while the row line says `PASS` and `_exit_code` (scheduler.py:498–501) returns 0: the gate says PASSED under a block that says FAILED, and the owner's required output (decision 9) is silently missing. In CI the design's `_law_block_ci` keys on `verdict != "pass"` only, so the same record prints `[*[], "", *table]` — a blank first line, no block at all (`summary.render` line 121 of the note).
Disposition: §2.5 — in `scheduler._finish`, `done.id == "lawdelta" and decided.ok and law == []` flips the verdict to fail with reason `lawdelta: exit 0 but law.txt is empty or missing` (the record then carries `verdict: "fail"`, the block prints FAILED, the gate is red); in `summarize`, `_inconsistent` gains `record["id"] == "lawdelta" and record["verdict"] == "pass" and not record["law"]` → `inconsistent: pass with no LAW Δ block`. Name the two tests (`test_lawdelta_pass_without_law_txt_is_a_failure` in test_main/test_scheduler; `test_a_passing_lawdelta_record_with_no_law_is_inconsistent` in test_summarize). Also say `law.txt` is written with `records.write_atomic(path, text.encode("utf-8"))` so a kill mid-write leaves nothing, never half a block.

### S2 — should-fix: text (v) is untrue under `--job` (§2.5)
Evidence: CI runs every job as `gate/bootstrap.py exec -- --tier T --job <job>` (generate.py:80); `registry.select(rows, tier, job)` (registry.py:234–240) narrows `self._rows` to that job. In the `test`, `proofs`, `race`, `determinism` jobs' own summaries the design prints `LAW Δ: not run — the lawdelta row is not in this registry at T4`, which is false (it is in the registry, in job `lint`). Same at `make check --job x` locally.
Disposition: §2.5 — key the text on the selection scope string `select` already builds (registry.py:240: `tier` or `f"{tier}, job {job}"`): `LAW Δ: not run — the lawdelta row is not in this registry at T4, job proofs`; that sentence is true. The P1 (v) text is unchanged for the `--job`-less case. Add the case to `test_main.py` (`test_a_job_selection_without_lawdelta_names_the_job`).

### S3 — should-fix: `git diff --numstat -z` emits a different record for a rename; the design's parser would crash or misread (§2.2)
Evidence: probe on 608ea58 (a rename): `0\t0\t\0docs/…/g01.cep\0docs/…/rev5/g01.cep\0` — an empty path field then two paths. The note's `numstat` returns `(path, added, removed)` and says nothing of renames; git detects renames by default. An ADR or baseline file renamed on a branch makes the row exit 2 (`internal error`) — the gate is red for the right reason by accident and the block is lost.
Disposition: §2.2 — `git diff --numstat -z --no-renames <base> <head> -- <paths>`; a rename then reads as `−N` on the old path and `+N` on the new (and `delta(kind, old, None)` / `(None, new)` on each), which is the honest law reading. `test_git.py` gains `test_numstat_reports_a_rename_as_a_removal_and_an_addition`.

### S4 — should-fix: `parse`'s regex with `$` accepts a trailing newline (§3.2)
Evidence: Python's `$` matches before a final `\n`; with `re.match`, `parse("S1.1c-1\n")` succeeds, breaking "over the exact text (no stripping)" and `canonical(parse(x)) == x`. `read_marker` guards its own call, but lane A's `marker` parser, `load_order`, `load_entries` and S1.1c-2's `todocheck` all call `parse` directly.
Disposition: §3.2 — `re.fullmatch` (state it); the error list of the plan check §6 (2) gains `"S1.1c-1\n"`.

### S5 — should-fix: every G0 file has a top-level `note`; four loaders as specified would reject the real files (§2.3, §3.2, §3.3, §5.2)

### S7 — should-fix: `go list -m -json all` is a stream of JSON objects, not an array; and `go mod graph` holds `go@`/`toolchain@` nodes (§5.3)

## Pre-mortem — three ways this fails us by S4.2
1. The block becomes wallpaper: every PR touches `gate/runner/` (kind `code`), so the block is never `none`; the owner stops reading it and a `doc` line slips by. Mitigation: print `code`/`workflow` lines last, grouped as one line (`gate/runner/: 7 files +120/−40`).
2. The `deps` row goes red on every toolchain or dependency bump for a reason unrelated to the tree (B1, S7) and the allowlist gets edited reflexively; the owner learns to re-run instead of read. Mitigation: B1's setup step and S7's drops before the row lands.
3. `SCHEMA` bumps become routine: `_valid`'s exact key set means every new record field is a schema bump and a fixture sweep; by S4.2 someone adds a field without the bump and CI reads every record as malformed. Mitigation: `_valid` also asserts `record["schema"] == records.SCHEMA` so the failure names the schema, not "malformed".
